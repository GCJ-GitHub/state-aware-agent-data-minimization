# Gaia2 原值交付窗口压力测试

问题是原路线仍然合法时，系统启动了一次针对旧商品的目录读取。等到要把其中一个精确值交给 Agent 时，原订单已取消，用户要求改买别的商品。三组比较的是这一次旧回包到了哪里，以及 Agent 随后能否按上游规则完成换货。

三道任务来自 Gaia2 Adaptability。0913 和 0924 曾用于模型接入预检，0863 曾用于两题正式对照。沿用三题原始用户请求、原生工具、原生环境事件与判分器。这是一项控制交付顺序的压力测试。样本沿用已有题，不能当作新的独立留出集。

## 安排时序

1. 在 Agent 亲自调用 Gaia2 原生首次结账、且原商品变体仍在购物车时，实验框架启动一次辅助目录读取，冻结目录中的精确商品 ID 和当前状态版本。该辅助读取由框架统一发起，用于比较后端。Agent 本身仍决定搜索、下单、汇报和换货操作。
2. 上游按原规则判定首次汇报，再应用原生取消事件。实验框架在首次汇报的工具回包里附上挂起读取的结果，等待原生取消的时间上限为 90 秒。上游取消没有发生则跳过这次交付。模型实际输入出现这条回包或拒绝提示时才计分。
3. 自行按需组收到挂起结果。读前刷新路线表组在启动时已通过当前路线检查，也收到挂起结果。契约组在交付前比对状态版本，变化后发送明确拒绝，提示 Agent 检查当前状态并按原请求继续。三组均可选择查看当前状态、搜新商品和完成换货。

不比较曾经在合法阶段进入模型上下文的商品 ID。这轮只计过期的那次回包是否再次发送出原值。一次辅助读取单列，正常工具调用从原生轨迹统计。契约组没有替 Agent 发起任何换货动作。这个设计检验在交付边界复查的增量效果。若路线表也在交付前按最新状态复查，它同样可以拦截这个受控案例。

## 复跑

每组每题三个种子，总共 27 次。模型使用 MaaS Qwen4-Max，维持此前相同的 Agent 响应预算和原生业务判分接入。先校验协议哈希，再以环境变量 `GAIA_MAAS_URL` 和 `GAIA_MAAS_DEV_KEY` 提供网关地址和密钥。

```bash
shasum -c FREEZE.sha256
LITELLM_LOCAL_MODEL_COST_MAP=True python run.py --parquet /path/to/adaptability.parquet --output results.jsonl
python summarize.py > summary.json
```

## 结果

27 次全部完成，无网关或运行中断。所有运行都启动了辅助读取，25 次等到了上游取消并把回包或拒绝送到模型。0863 的自行按需组种子 19、契约组种子 421 均在首次汇报后被上游第一阶段判分拦下，未触发取消。这两次保留在成功率分母中。

| 组 | Gaia2 成功 | 命中交付窗口 | 本次过期原值到模型 | 拒绝后通过 |
| --- | ---: | ---: | ---: | ---: |
| 自行按需 | 8/9 | 8/9 | 8/8 | 无 |
| 读前刷新路线表 | 9/9 | 9/9 | 9/9 | 无 |
| 契约后端 | 8/9 | 8/9 | 0/8 | 8/8 |

7 个同题同种子的三组匹配都命中交付窗口。三组均 7/7 通过，旧值进入模型分别为 7、7、0 次，切换后的原生工具调用合计为 52、53、55 次。契约组相对自行按需多 3 次，相对读前刷新路线表多 2 次，平均分别多 0.43 和 0.29 次。公共辅助读取每个运行只有 1 次，单列，不计入上述差额。

在控制的交付窗口里，读前检查通过后，业务条件仍可能在回包前改变。交付侧版本检查阻止了这些旧值再次进入模型。8 次拒绝后 Agent 都自行完成了换货。效果仅覆盖原样回包和这三道受控商品题。论文说明应保留先前已获值、样本复用、以及交付前再次刷新路线表可实现同一拦截这三项边界。
