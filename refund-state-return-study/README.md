# 多次状态切换下的退款读取授权

使用同一个 MaaS Qwen4-Max，在五种合成退款轨迹上比较两种后端，每个场景每组使用种子 19、113、421，总计 30 次正式分派。退款、确认与账户引用均由本地模拟器提供。沿用既有退款工具、路线优先级、确认规则、路线表、契约验证器、拒绝恢复提示及原生工具调用解析。

Agent 自己查状态、选路线、准备读取和尝试交付。第一次有效的银行读取准备好后，可信模拟器在这次读取交付前应用该题的整段状态变化。所有场景均在银行路线合法且钱包不可用时发出旧读取。Agent 无法控制这些变化。正式记录包括实际事件序列、旧授权判定、拒绝原因、最终业务提交和工具名称。

两组都在交付前刷新当前路线、检查授权是否撤回过、检查原来请求的字段是否改变。路线表使用同一份明确写出的授权代数和字段版本规则。契约组另外使用仓库现有的版本化计划验证器，检查签发时的计划支持证据版本。这个条件对钱包优先级证据也生效。账务操作仍由共有的确认与提交校验处理。

| 场景 | 冻结的旧授权判分 | 应完成的退款路线 |
| --- | --- | --- |
| 银行 → 钱包 → 银行，银行授权始终有效 | 允许复用，当前目的恢复，授权和字段均未变化 | 银行 |
| 银行 → 钱包 → 银行，原银行授权撤回后重授 | 拒绝旧授权，重授后的请求需重新取得授权 | 银行 |
| 只改内部工单备注 | 允许复用，备注与路线和字段无关 | 银行 |
| 银行引用更新 | 拒绝旧请求，重新获取当前银行引用 | 银行 |
| 银行 → 钱包，交付时仍使用钱包 | 拒绝旧银行读取，改走钱包 | 钱包 |

旧授权在冻结条件下应当有效却被拒绝，计为误拒绝。应失效却交付，计为误放行。业务成功要求只提交一次正确的退款。切换后调用从第一次旧读判定结束计到提交，包含正常完成、重新查状态、选路线、取数与确认。另报拒绝子集的恢复成功和调用，并以同题同种子对比较调用差值。

预跑发现个别模型在已完成退款后反复发状态工具调用。保留四条预跑诊断，正式实验在共有的业务提交边界终止，邮件式最终汇报不计分。状态变化、冻结标签和读取规则从预跑到正式实验保持一致。十个机械复放检查都通过，验证了事件可触发、旧授权判定符合各实现以及两组均存在可提交的合法后续轨迹。

## 实测结果

正式矩阵 30/30 次完成，五个场景各有三个有效匹配对。没有传输中断或不正确的退款提交。

| 指标 | 交付前刷新路线表 | 契约后端 |
| --- | ---: | ---: |
| 正确退款 | 15/15 | 15/15 |
| 允许复用旧请求 | 6 | 3 |
| 误放行 | 0/9 | 0/9 |
| 误拒绝 | 0/6 | 3/6 |
| 拒绝后正确退款 | 9/9 | 12/12 |
| 旧读判定后工具调用 | 66 | 78 |
| 全程工具调用 | 126 | 138 |

银行授权持续有效的往返场景出现了全部差异。三次中，路线表复用旧授权，契约组都因钱包的可用性证据版本改变而拒绝。实际账户引用、持有人引用及银行授权均未变化。契约组每次需要额外查状态、重选路线、准备和读取，共多 4 次业务工具调用。平均分摊到 15 次，契约组每次多 0.8 次。纯备注变化时两组均复用。授权撤回重授、账户引用更新、以及钱包保持可用时，两组均拒绝旧请求并正确恢复。九个双方都按规则拒绝的匹配对里，旧读判定后工具调用均为每组每次 6 次。

结论依赖该退款业务允许持续授权下的暂时路线切换。以此为准，现有契约绑定的支持证据比授权连续性规则更严格。路线表在交付前也验证撤回代数和字段版本，具备相同的安全结果，并在该轨迹上少一次重新取数流程。这五个受控样例检验判断规则及恢复路径，可用于定位条件和开销来源。任务终止延迟、真实退款系统与自然发生频率不在本实验范围。

准备正式执行时曾修正评分器漏传工具序列，错误批次没有生成结果行。以上数字全部来自修正后完整重跑。
