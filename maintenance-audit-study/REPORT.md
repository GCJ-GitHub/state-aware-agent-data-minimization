# 读前刷新路线表与契约后端的维护和审计对照

## 变更任务

在上一轮自主对照的退款和自提规则上，加三条相同的业务要求。两组沿用相同的优先级、字段授权、审批和业务执行器。这里用脚本走工具阶段，排除模型行为。配置、用例、计分代码和依赖在执行前做了哈希冻结。

| 规则 | 触发条件 | 新前置核验 | 受影响的操作 |
| --- | --- | --- | --- |
| R1 | 银行收款资料最近变更 | 核验收款人引用 | 银行退款 |
| R2 | 自提点变更跨区域 | 核验承运申报引用 | 变更自提点 |
| R3 | 自提点需预约资质核验 | 核验预约资质引用 | 首选和备选预约 |

路线表的一条预约片段选择器可覆盖两个预约变体。当前契约配置按工具名匹配。两组都以同一套迁移思路编译条件分支。迁移代码和路线分组标签是实验接入成本，未计入每次配置修改量。

## 维护结果

| 指标 | 读前刷新路线表 | 契约后端 |
| --- | ---: | ---: |
| 人工新增业务声明 | 3 | 3 |
| 声明中需填写的目标条目 | 3 个路线片段 | 4 个工具名 |
| 公共执行目录内变更的已有操作 | 4 | 4 |
| 公共执行目录生成的新操作 | 7 | 7 |
| 变更的已有路线表条目 | 4 | 0 |
| 生成的新路线表条目 | 4 | 0 |
| 正确配置验证通过 | 36/36 | 36/36 |
| 非触发条件的旧流程回归一致 | 12/12 | 12/12 |
| 注入误配被回归发现 | 15/15 | 15/15 |

每组旧流程的 12 个回归用例覆盖六种原有行为，分别是钱包退款、银行退款、无可用退款路线，以及自提点变更后走首选预约、走备选预约、无可用路线。每种行为核对两种新增字段授权设置。新条件关闭时，前后比对执行步骤、提交分支、交付字段和批准次数。三项新条件打开时同时测试核验值获准与未获准，且覆盖跨区域和预约资质规则同时生效。本轮回归是这些合成支路的脚本复跑。

误配测试对每条规则各注入一次漏规则、选错目标、条件反写、字段错绑、漏接依赖。每组 15 种误配均在至少一个用例触发结果差异，每组累计 84 条用例差异。同一种误配可能同时导致多读、漏核验或错误放行。误配数由实验者设定，这个结果衡量回归能否发现已知错误类型，实际人员的误配率和修改耗时仍需人工维护对照。

## 审计结果

在退款上每组构造 8 个审计事件。检查正常放行、核验后放行、未获字段授权、缺前置核验、请求字段错误、资源错误、路线改变、仅版本变化。把两种日志能力分别计分。

| 日志能力 | 读前刷新路线表 | 契约后端 |
| --- | --- | --- |
| 原生读取成功事件 | 此接口未发出 | 两次成功案例均发出，记录步骤和字段名 |
| 原生拒绝信息 | 可见 5 次异常文本 | 可见 6 次异常文本 |
| 原生日志直接包含业务规则 ID | 0/8 | 0/8 |
| 共用结构化日志后可重建判定原因 | 8/8 | 8/8 |
| 用批准规则与已部署配置复核误配，可定位注入原因 | 15/15 | 15/15 |

原生日志里，契约后端对钱包恢复和仅版本更新均返回“支持证据发生变化”。它记录了发生过读取和哪些字段被读取，但规则 ID、变化的具体状态以及前置核验仍需另记。路线表对钱包恢复给出“当前证据不再支持计划”；仅版本变更时放行。两组统一记录实际判定、请求步骤、请求与所需字段名、规则 ID、核验状态和前后证据版本后，都可以从记录中重建原因。重建是程序按冻结案例判定，未测人工排障速度。

在配置本身写错的场景，日志只能描述系统依据什么放行。排查程序用冻结的批准规则和实际编译配置做对照，才识别规则遗漏或错误映射。诊断记录附一条对应回归反例。日志样例仅保留字段名和合成状态。

## 结论

契约后端减少了这套实现中的派生路线条目，人工声明数量持平，路线表的分组能力在这批规则中还少填一个目标。两组在回归、注入误配检出和结构化审计上持平。契约原生成功记录提供了更多可追溯信息；完整的放行与拒绝解释仍依赖显式审计记录。这批证据支持报告具体的配置和审计差异，维护优越性仍缺少人工用时和自然误配数据。

## 复跑

在仓库根目录执行以下命令，已有冻结清单可直接验证。

    python maintenance_audit_study.py run
    python maintenance-audit-study/fault_audit.py

results.json 保存正确配置、回归、误配和审计数据。fault-audit.json 保存误配归因的配置证据。
