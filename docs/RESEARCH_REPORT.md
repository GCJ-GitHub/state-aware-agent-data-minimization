# 研究说明：idea、证据、算法与下一步

记录日期：2026-11-19。请连同README、逐轮报告、原始轨迹及透明性说明阅读。

## 1. 我们实际研究什么

Agent需要接触个人资料才能执行操作，但很多字段只在某条分支上才需要。任务开始时，只知道“可能要处理什么”；查到真实业务状态后，才知道“这一步实际要做什么”。

例：用户允许原路退款，若失败也允许银行退款。两类引用都已授权，但能够原路退款时，没有必要把账户引用送给执行模型。数据已获准用于某个可能情形，并不自动意味着本次路径需要它。

研究对象是数据进入模型的时间和范围，不是训练模型记住隐私标签，不是给模型加一句“不要泄密”，也不是把一个普通字段过滤器当作全新算法。

## 2. 相对AirGapAgent的边界

AirGapAgent使用可信用户任务和隐私要求建立base context，先最小化资料，再让隔离的对话Agent处理第三方请求；第三方不能直接改变最小化模块。原文也讨论缺资料时向用户升级请求。因此“他们不能补取，我们首次按需取数”是不准确的。

本研究把关注点放在动态业务状态：同一句任务、同一资料、同一授权，在工具确认不同状态后，实际必要字段可能不同。我们尝试利用可信服务状态自动收窄每一步的信息释放，同时阻止第三方自由文本直接扩大授权。

当前A组是“事前给齐所有已授权候选字段”的具体基线，不是完整原版AirGapAgent复现；当前规则也是人工编码的，不能把其结果等同于原论文最小化模型的结果。

若比较模型服务本身接触了多少数据，还必须明确边界：执行Agent、最小化模块、后端数据仓与模型提供商是不同主体。原论文的第三方上下文劫持防护，与“外部模型提供商不接触多余资料”不是自动相同的威胁模型。

## 3. 方法结构

1. 用户请求规定可用路线、优先顺序和确认条件。
2. Agent自己调用状态工具，获取当前单元的可行路线和元数据。
3. Agent自己选择路线并调用准备工具；后端共同校验授权和优先级。
4. 若缺少值，Agent自己调用数据工具。
5. C组额外根据真实后端状态、已校验路线和字段需求过滤返回值。
6. Agent按同一确认规则发起确认与执行；状态变化后重新查询，直到全部单元完成。

状态来自模拟后端事实，不来自Agent自称“现在需要这个字段”。读取限制不修补工具名，不编造参数，不替Agent执行。

## 4. 三个策略

- **A：事前给齐。** 框架在首次状态查询前提供全部已授权候选路线字段；Agent可以直接使用，必要时也可读取。
- **B：自行按需。** 初始化没有字段值，提示与C相同；模型自己决定读什么。仍有所有组共同的全局授权、路线与执行校验，但没有当前状态的额外字段过滤。
- **C：后端按状态。** 初始化同B，只返回已准备当前路线所需的字段；查状态和准备路线之前不给个人字段值。

在最新两个模型中，B/C没有请求到需要状态拦截的字段，C的状态过滤未触发。因此本轮支持按需策略的可行性，未证明强制过滤提高实测隐私或成功率。安全兜底的机制存在，不等于它在这些样本上产生了额外收益。

## 5. 为什么要统一呈现位置

早期完整三组对照将A的预取值放在SYSTEM，B/C通过工具取得值。这同时改变了放行时机和信息呈现位置，不能把成功率差完全归因于延迟取数。

后续修正：三组SYSTEM不含个人值，初始化与后续数据均使用相同工具回包。18个失败任务的诊断复测中，A从54/54变为52/54，B/C从4/54变为30/54，说明之前的结果需要谨慎解释。但这批题按失败选择，不能据此更新全量任务成功率，也不能把全部变化归因于A字段位置一个因素，因为B/C也有了共同的空初始化回包。

最新完整新任务集采用中立JSON文本调用协议，所有模型和组别的字段值都通过同格式工具回包进入上下文。正式任务开始前，非数据集协议探测发现原生模板复制会导致MaaS重复标签，于是改为统一单JSON调用格式；预运行修正记录保留，未根据正式任务输出来调提示。

## 6. 最新任务怎么构建

120个任务来自60个配对。每对用户请求、资料、授权、优先级和单元结构完全相同，只有隐藏业务可行状态不同。三种流程各40题，三个业务场景各40题。

- 单分支：查询后选择一条可用且获准的路线，执行一次。
- 中途换分支：第一次按当前信息合理执行时，业务报告可用性改变；重新查状态、补取新路线数据，再完成同一单元。
- 多单元：明确区分2或3个包裹、购买行或预约项目，每个单元只成功执行一次，不能同一笔退款重复执行来充当多阶段。

每个单元拥有独立字段命名和引用，避免把第一单元的值错当成第二单元。授权路线为3或4条；可行列表可能出现被用户禁止的路线，三组共同拒绝它。部分用户要求所有动作确认，另一些路线只在敏感动作时确认。

资料为合成地址、邮编、电话与引用。字段间避免完整值包含，减少按值检测时的交叉误报。措辞组合、优先级、授权与可行列表有变化，但不应把36个措辞/场景组合当成36类独立语义任务。

## 7. 模型与固定设置

| 项目 | 设置 |
|---|---|
| 本地模型 | MLX Qwen3-1.7B-4bit，Apple Silicon GPU |
| 服务模型 | MaaS别名qwen3.8-flash；仅记录实际返回版本，不推断参数量 |
| 每组 | 120任务×3次=360条完成轨迹 |
| 温度/种子 | 0.3；19、113、421，具体每任务随机种子变换见代码 |
| 输出上限 | 每轮192 token |
| 轮数上限 | 每任务24轮 |
| 推理 | 本地关闭；MaaS请求enable_thinking=false |
| 停顿恢复 | 每任务最多两次，相同提示 |
| 数据回包 | values、denied_fields、feedback，同一格式 |
| 初始化 | 每任务一次框架快照；A带值，B/C空；不是伪造的模型调用 |

MaaS使用4个并发评测流程。两个模型的请求输出上限相同，不代表tokenizer或隐藏计算完全相同。服务种子是请求参数，不是已验证的服务端确定性保证。

## 8. 怎么评分

**任务正确性。** 后端终态、实际路线顺序，必须与独立答案表一致；另外核验每次有效操作的单元ID、所需字段、具体值和确认。不能只信一个success标记。

**多读。** 对每条轨迹，记模型实际接触的字段集合，扣除完整正确路径的必需字段并集，再去重计数。重复实验求和时，叫“字段次”。

**过早读取。** 单独记录读取时尚未属于当前已准备路线的字段。它与多读可能重叠，不能相加。

**输出。** 对完整字段值做大小写与空白规范化匹配，带词边界。分别记录未用字段进入非工具文字、未用字段进入执行请求、旧合法值进入错误步骤，以及任一个人值进入非工具文字。

无效JSON或被截断调用中的值可能计入非工具文字；这与已经交付用户的最终答复不同。执行请求在本地模拟，非法请求会被拒绝；日志中的错误请求不是实际对外转账或第三方泄露。

**成本。** 统计Agent调用、模型轮次、逻辑输入/输出token、模拟确认、恢复和截断。初始化回包单列。MaaS的实际usage、HTTP尝试和限流另列，不能用主表冒充完整账单。

**不确定性。** 按60个原始状态配对聚类，保留每对两个状态及每题三种重复，bootstrap 5,000次。三个种子不是三倍独立新任务。所有样本成功产生的零差区间不意味着未知分布的风险也严格为零。

## 9. 最新结果的解释

完整表见README与最新REPORT。核心结果：

- MaaS三组360/360；两个按需组将1,605个未用字段次降为零，实际读入字段次2,382→777。后端组工具调用增加22.3%，每任务增加约1.46次；确认不增加。
- 本地A为339/360，B/C为268/360。后端组比A少71次成功，多2,170次工具调用；成功率差约19.7个百分点，配对95%区间约13.3–26.7个百分点。
- 本地A有56条轨迹把全流程不需要的值放进执行请求，B/C为零；但B/C仍会错用以前合法拿到的值、生成包含个人值的格式错误文本，不能称所有输出零泄露。
- MaaS的A本来就没有观察到未用值输出，所以本轮不能声称MaaS最终回答隐私优于事前组。确定的收益是少让模型接触资料。
- 本地B/C指标完全相同，MaaS两组也近似相同且状态过滤未触发。额外校验没有测出增益。

在这套协议和任务中，小模型的性能损失不是“所有模型都必然损失”的证据；较强服务模型证明了保持操作正确性的可行性，但不保证其他模型和真实业务也如此。

## 10. 限流、重试与审计缺口

MaaS的10,015次HTTP尝试中有751次429。9条评测流程中断后重跑，额外产生33个成功中间返回。计入重跑后，每任务成功返回的模型轮次仍未超过24，但网络尝试次数可能更多。

完成轨迹计数与HTTP尝试A/B/C分别为：模型轮次2,728/3,251/3,252；HTTP 2,954/3,547/3,514。首次流程没有中断并完成的数量为356/357/358。

中断流程未保留完整动作历史；不能将完成轨迹的零泄露观察外推到所有中断过程。审计验证的是2,160条完成轨迹中的27,065次实际模型输入和工具事件。历史缺失无法靠事后再跑同题找回。

## 11. 早期实验各自能说明什么

- 物流1–5轮：从选字段/框架执行逐步转到模型自主调用，修复工具格式、拒绝后继续取数等问题；多数是开发与诊断。
- 物流6–11轮：新增订单、路线偏好与授权条件，后来加入状态前路线校验和停顿恢复，另有规则提取试验；不能把多轮累计修复当成同一个未见测试集结果。
- 物流与退款放行时机对照：检验字段暴露是否跟随真实状态改变，冻结恢复规则后的新退款任务用于有限复现。
- AirGapAgent-R：区分原公开题和自建状态派生题；隐私/效用分是小样本的论文式口径，不是完整榜单。读取时机不能自动纠正错误的授权白名单。
- 推理与诱导：记录可见思考与回答的完整值出现，若接口不给思考则不能记零；重答规则经过开发批次迭代，后续留出题另报。
- 四个MaaS模型：验证部分小样本现象能跨服务出现，但各服务思考预算不完全统一，不能与本地逐token预算作严格算力比较。
- 初次完整三组：有字段呈现位置混杂；18失败任务修正只是诊断。最新跨模型完整新任务集是当前主结论的主要证据。

每一轮代码、任务、原始轨迹与当时说明都保留，入口见EXPERIMENTS.md。历史诊断也保留，不只挑成功结果。

## 12. 可以收敛的课题表述

“面向动态业务状态的Agent阶段性数据最小化：在既有授权范围内利用可信状态延迟释放当前不需要的数据，研究数据暴露、任务完成率与调用开销的权衡。”

当前贡献候选包括问题定义、状态配对任务与指标、可复现控制器原型，以及模型相关的实证权衡。尚不宜宣称新的通用访问控制原理、全面SOTA或后端过滤优于自行按需。

## 13. 下一步按优先级推进

1. **先写现有方法、实验和限制。** 不继续在同一测试失败题上补提示再报告满分；方法修改应回到开发集，另留未见测试。
2. **若论文要主张对AirGap式方法的改进，补强事前基线。** 使用同一授权与工具，保守地给首选路径必需字段，缺失时按固定升级规则补取；量化多读、完成、确认与调用。完整原版复现则还需报告最小化模块及其输入/额外调用，不能以手工规则冒充。
3. **若强制校验作为核心贡献，才补压力测试。** 用冻结的诱导多取、错单元字段和状态变化请求，衡量B是否过读、C是否挡住、是否影响合法任务。现有普通任务没有触发状态过滤。
4. **完善日志再做真实工具。** 保存中断前每次实际输入、返回与动作，按步骤恢复并使用幂等键；不可重新执行已提交退款等动作。当前只有模拟环境。
5. **外部有效性。** 可选择外部作者任务或真实格式的隔离测试数据，并检查从用户原话提取授权/优先级的误差。当前人工规则不是完整生产系统。

这些不是必须一口气全部做的清单。立项价值已有证据；论文想主张多强，才决定还需哪项验证。

## 14. 当前明确未验证的主张

绝对零泄露；隐藏思考安全；部分值与语义推断攻击；对未授权真实工具有通用防护；真实用户体验改善；所有模型效用无损；跨服务计算预算完全相同；完整AirGapAgent胜出；自动授权规则提取在真实业务可靠；真实服务端状态来源始终可信。
