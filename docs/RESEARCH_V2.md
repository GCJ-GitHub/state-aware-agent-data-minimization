# 深化方案：面向动态工具任务的可验证按需取数

日期：2026-11-23。状态：问题定义、可运行离线原型、正确性检查和后续实验设计。**本次没有调用 MaaS 或本地模型，没有新的 Agent 成功率/安全提升结果。**

## 1. 研究问题应落在哪里

旧实验研究：当前路线确定后，只给当前路线的字段。这个方向已经有稳定的少读取结果，但强模型自行按需也能做到，且路线所需字段由工具明确告知。继续换订单不能自动增加方法创新。

深化后的问题是：**任务有多个合法完成计划、必要信息尚不完整时，如何决定先查询什么、哪些原值值得进入模型，并验证每次取数确实服务于当前获准计划？**

候选贡献应在以下三件事的结合中寻找，而不是在“后端拒绝请求”这个组件上：

1. 从基础工具依赖和可信业务证据推导当前的读取范围，减少对每订单、每状态最终字段表的依赖。
2. 显式处理“为了选路线而取数”：允许先返回获准的判断结果，选择查询顺序，记录后端实际读数和模型得到的信息。
3. 在多合法计划下区分可行、符合用户效用要求、披露成本更低；状态变化后重新验证理由，包括先前排除更优分支的负面证据。

这目前是**值得检验的贡献假设**，并不是已经确认的新颖算法。

## 2. 一个普通人能理解的例子

用户说：“钱包和银行退款都可以，两天内到账、手续费不超过三元即可；满足这些条件后，尽量少使用个人资料。”

- 钱包退款执行需要一个钱包引用。
- 银行退款先验证账户，通常需要账户引用和所有者引用；高额退款还需要身份验证。
- 现在不知道钱包的费用和时效是否满足要求。

此时直接说“当前没选银行，任何银行相关查询都不必要”并不充分：路线本身尚未确定。也不能为了判断路线，把费用、时效、钱包、账户、身份资料全部送给模型。

可行流程是：

1. Agent 调用获准的固定判断接口，查询钱包是否满足费用/时效条件。
2. 后端计算并返回判断结果，模型不必收到准确费用和天数。判断结果本身仍是信息披露，后端读取也计数。
3. 根据工具依赖展开可行计划：钱包一个字段；普通银行两个；高额银行三个。
4. 先满足用户效用要求，再按用户明确的隐私偏好比较字段成本。若用户更偏好银行，不能为了少读而强迫走钱包。
5. 每到一个执行步骤，只放行该步骤尚缺的原值。Agent 自己提出计划、查询和执行；校验器不代替模型补工具调用。
6. 如果钱包条件在取数前改变，旧的取数理由失效，重新取证、选计划。已经给模型的值无法靠撤销权限“收回”。

如果用户要求“给我准确的两项费用再决定”，原值就是合法目标的一部分，应允许读取。固定的“是否低于三元”接口也不能解决用户要求找最低价格的所有情形；那需要额外获准的比较接口或原值。

## 3. 和现有工作的关系

本次查阅的是针对候选贡献的文献定位，不是穷尽性系统综述。以下描述只用于划清已有基础，不能据此断言某论文完全没有候选能力。

当前拟检验的差异更具体：**在信息不完整、多种合法计划并存的情况下，计算并验证读取理由，优化获得这些理由的查询过程。** 需要逐项核对近邻工作和实现，不能仅换术语声称原创。

## 4. “必要”需要重新定义

### 4.1 不再假设只有一条正确路线

在工具契约 C、原始用户授权 U、目标 G 下，定义结构上可用的计划集合 Π(C,G,U)。每个计划 π 包括工具节点、数据依赖、条件和输出。

计划的执行原值集合：

`R(π) = union(所有计划节点声明的原值输入)`

如果钱包和银行都合法，`{wallet_ref}` 和 `{account_ref, owner_ref}` 都可能是有效完成集合。不能简单把一条参考路线之外的所有字段都判成违规。

- **超出所选合法计划的读取**：需要解释并可能拒绝。
- **选择了一个合法但披露成本较高的计划**：属于效率差距，未必违反授权。
- 只有用户明确要求在同等效用下最小化披露时，才将这一偏好作为选择约束。

### 4.2 用户效用优先于省字段

原型使用一个简单的字典序目标：先最小化用户定义的路线优先级惩罚，再在明确要求时最小化 `sum(field_cost)`。默认字段成本均为 1。

多目标任务的优先级惩罚采用显式的可加简化，不代表所有用户偏好。字段成本也是代理指标，不等于隐私损失；不同属性的敏感性和实际信息量不能由字段数量自动表达。

### 4.3 事前正当读取和事后用没用，是两种指标

一个字段可能是为了判断路线才合法读取，最后却没有出现在执行参数里。仅用“最后没用”判定过度读取，会误伤合理决策。

新评测应至少区分：执行必需原值、获准的决策信息、超出理由范围的读取、提前读取、事后未使用值，以及下游泄露。可以构造两种与已有证据一致的业务世界，检验某个未知条件能否改变合法/最优计划；这种相关性见证不意味着它是所有策略下都不可替代的唯一查询。

## 5. 机制与信任边界

### 5.1 基础工具契约

每个基础工具登记输入字段、前置条件、依赖的中间结果和输出。例如：

```text
验证身份 -> identity_verified
普通账户校验(account_ref, owner_ref) -> bank_verified
高额账户校验(account_ref, owner_ref, identity_verified) -> bank_verified
银行退款(account_ref, bank_verified) -> refund_done
钱包退款(wallet_ref), 费用/时效条件成立 -> refund_done
```

展开目标的 AND/OR 依赖后，才得到每条计划需要的字段，合并共享依赖。不存在按订单编号查最终 `allowed_fields` 答案的表。

**但契约仍由开发者/工具所有者维护。** 把旧映射搬进 JSON 并不自动构成创新。原型的新增能力是跨步骤组合、条件依赖、替代计划和共享依赖的推导；没有自动理解任意 API 的真实语义。后续应从 OpenAPI、服务代码和人工验证注释建立契约来源，并实测注释与维护成本。

### 5.2 不完整证据与安全等待

前置条件为真、假或未知。未知不能被模型的自称、第三方文字或高概率预测代替。

如果某个尚未排除的计划可能比当前已证明计划更符合用户目标，返回缺少的证据；Agent 需要自己查询。若低优先级未知路线不可能改善当前目标，不强求查询它。没有合法计划时明确返回不可完成，不编造状态。

### 5.3 判断结果优先，但不制造“系统零接触”假象

原型只支持登记好的固定问题，不允许模型不断调整阈值、查询任意订单或任意字段。查询返回签名的布尔结果，后台读取计数，结果披露计数，重复同版本查询缓存。

这不是差分隐私或通用安全聚合。单个判断、路线选择、错误、时序以及跨任务重复提问仍可能泄露信息；需要单独的查询预算、输出策略与威胁分析。后端看过原值的成本绝不能藏在“模型没看到原值”后面。

### 5.4 每一步的读取理由

校验 Agent 提出的计划是否来自获准工具、是否实现目标、是否存在多余节点、是否有可信条件支持、是否满足用户偏好。对一个依赖已完成的待执行节点，发放绑定资源、节点、字段版本和证据版本的一次读取凭据。

该理由是**给定契约和证据下的计划见证**，不是对现实世界绝对必要性的数学证明。原型拒绝超范围字段、伪造事实、跨订单复用、重复使用和旧版本数据；执行参数仍需与当前实际值一致。

### 5.5 状态变化还要看被排除的路线

只绑定当前银行路线的事实不够。例如，先前钱包不可用使银行成为正确选择；钱包重新可用时，即使银行状态没变，银行的最小披露理由也可能失效。

因此原型也绑定排除替代计划的相关证据版本。无关 UI 状态变化不会撤销读取；相关负面证据或输入值变化会要求重新验证。目前绑定是保守的，并非最小证据切片算法。

### 5.6 尚未覆盖的系统安全

工具与契约可信、初始授权正确、状态来源真实、所有读取与执行被完整接管，是当前信任前提。原型是单进程顺序执行的模拟，没有跨进程/分布式事务和并发原子性保证。

已完成副作用后的跨计划续接尚未实现；为避免模拟重复退款，原型会拒绝这类新计划。自然语言输出与任意下游工具的信息流隔离也未实现。已经进入模型上下文的旧值不会被“撤销”抹除。这些边界排除了生产安全或端到端零泄露的主张。

## 6. 查询顺序是可测量的算法问题

目前新增一个很小的精确参考器：在显式独立伯努利先验下，用标准动态规划计算为了证明当前计划目标，下一步查哪个固定条件的期望查询代价更低。它只使用已验证事实和工具结构，不偷看私有真值；概率从来不是授权证据。

例：钱包须同时满足费用和时效；不满足就走银行。假设费用达标概率 0.1、时效达标概率 0.9，每次判断查询成本 1：先查费用期望 1.1 次；先查时效期望 1.9 次。

这些是四个真值世界的加权精确值，不是模型实测。动态规划、短路查询和主动特征获取都有已有研究基础。本实现指数复杂度，只适合作为小规模比较上界，不能当作新的可扩展在线算法。

当前两级目标是“先确定用户效用/执行字段目标，再最小化证明它的查询代价”，尚未联合优化原值暴露、判断信息量、调用和时间。**真正有机会形成算法贡献的下一步**，是带预算的在线近似方法：在先验不准、工具延迟不等、状态会变时，少查信息并保留可验证执行路径，与标准贪心、固定顺序、模型自行选择及小规模精确参考比较。

## 8. 下一轮最小验证，不继续盲目扩订单

### 8.1 先检验新问题是否真的出现

先用独立开发任务接入真实自主工具调用，确认模型会面对以下困难，而非工具直接给出最终字段清单：

- 多条同等合法路线，隐私成本不同，允许用户偏好覆盖少读。
- 必须获得一点私有决策信息才能确定路线。
- 判断接口够用与用户明确要求原值两种相反条件。
- 组合任务、共享验证、条件性身份验证。
- 被排除路线变可用，或查询后数据版本改变。

不要用“多读字段最多”的方案反向生成唯一答案，不把脚本故意多取的轨迹冒充模型自主越界。

### 8.2 用分解对照回答不同问题

第一步可冻结 12 个新的困难任务，采用 2×2 对照、每组 3 次：

| 因子 | 条件一 | 条件二 |
|---|---|---|
| 查询选择 | 预先固定的合理顺序 | 给定先验的查询规划/推荐 |
| 执行约束 | 模型可使用相同规划器、证据接口及提示，但不强制读取理由 | 相同能力，再强制验证读取理由 |

共 144 条，先判断是否存在可测差异。这是下一步建议，尚未生成、冻结或运行这批任务。精确参考器只在小图使用；模型自行查询和标准贪心应作为后续强对照，不能只选择容易打败的固定顺序。

所有组必须能使用相同的判断接口、工具契约、规划辅助、数据呈现、确认与恢复，模型与预算相同。这样可以分开“更好的信息获取”和“强制拦截”，防止把工具能力差异包装成后端收益。

若确有差异，再按**未见过的目标/工具组合**划分较大测试集；不能仅换订单编号和值。加入充分预算的 AirGap 架构适配，最小化推理预算做敏感性检查。其整体架构比较与上述因果消融分别报告。

若要主张优于 CaMeL/CapAgent，必须有忠实实现和对齐威胁模型；仅借鉴组件的版本只能叫组件消融。人工全覆盖规则可作正确性上界，同时比较一次性基础契约维护与每工作流规则维护的实际成本，不能把注释数量直接当成人工工时。

### 8.3 计分不能只看原值字段

- 任务完成与用户效用；合法原值需求误拦截率。
- 对话模型原值暴露、获准判断结果披露、可信后端原始读取，分别计数。
- 相对合法计划集合的额外读取，以及相对最佳允许计划的成本差距，分开。
- 查询、执行、恢复、确认、实际 token/HTTP 成本；时间成本另测。
- 真实触发拦截及随后恢复，而非仅测试组件拒绝。
- 合法探索误判、过期证据放行、无关变更造成的过度失效。
- 证据/工具契约错误、自动意图编译错误与模型规划错误，分别归因。

在独立开发集检查诱导是否有效，冻结后完整保留测试结果。若模型自行按需始终零多读，就如实报告强制层没有额外实测收益。

## 9. 何时值得写成论文，何时应收缩

值得扩展的信号：在新组合任务中，可自动推导必要读取；少原值暴露并未转化为大量判断泄露或确认；查询规划相对强基线有效；用户确需原值时仍成功；可验证约束在真实错误上有收益而误拦截可控。

应收缩的信号：只有作者知道的状态表才能工作；模型获得同样接口后完全等效，系统也没有降低规则维护；所谓少读只是把原值藏到另一个同样不可信的模型；改进仅来自换了更强提示或更大预算；算法只是给已有访问控制加名词。

目前可诚实表述为：**已有实验支持按需读取的价值；新的原型把“必要数据从哪里来”变成可验证、可比较的问题。研究贡献是否足够强，仍取决于近邻工作的实质差异和下一轮难任务证据。**
