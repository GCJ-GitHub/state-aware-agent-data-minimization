# 物流工具按需取数实验

用同一句中文请求和 18 条合成订单比较两组。每种处理路径有 6 条订单，每条订单都跑两组，交替安排先后顺序。模型、提示、工具接口、业务规则和调用上限相同。工具通过进程内函数执行，每个任务最多调用 6 次，其中首次状态查询由实验框架执行。

| 物流分支 | 完成操作需要的值 |
| --- | --- |
| 原址重新派送 | 运单号 |
| 查询自提点 | 邮编 |
| 更换到已授权的备用地址 | 完整地址 |

两组的第一次状态查询都只返回物流状态、处理路径和运单号。Agent 可以通过同一接口补取邮编、完整地址和电话。校验组根据后端已确认的路径过滤返回字段，并拒绝状态查询前的敏感读取。后端只有在操作类型与路径一致且值精确匹配时才标记任务完成。

## 运行

使用 Python 3.11 和 MLX，模型参数指向已下载的 MLX 模型目录。本次使用 mlx-community/Qwen2.5-0.5B-Instruct-4bit、MLX 0.32.4 和 mlx-lm 0.32.2，推理全程本地执行。

补取阶段，模型给不同字段组合打分，实验框架把得分最高的选项转成工具调用。同一个组合在同一任务中只试一次。拿到操作所需字段后，框架提交业务调用。原址重派可直接使用状态查询返回的运单号。这里的成功率衡量模型选取字段后能否完成业务操作。自由生成工具指令的首跑单独保存在 `results-model-initial`，两组都卡在状态查询前。

```sh
python -m pip install mlx-lm==0.32.2
python run.py --model /path/to/model --out results-model
python run.py --scripted --out results-scripted
```

脚本组固定在自提和换址分支尝试获取所有字段，用于检查机制能否挡住多取。这组数据衡量校验机制的行为，模型组用来观察常规提示下模型实际如何取数。

`summary.json` 按组和分支汇总结果，`traces.jsonl` 保存逐任务调用和实际送给模型的工具响应。过度暴露以任务为单位，任意一次响应带回当前阶段不需要的敏感字段就计入，任务内重复字段只记一次。单独记录完整地址暴露、任务成功、调用数和无效输出。任务耗时包含本地推理与业务调用，后端耗时仅衡量进程内业务调用。耗时受热身和本机负载影响。

这是探索性实验。样本是同一请求和少数业务模板的变体，结果适用于该模型、提示和模拟环境。
