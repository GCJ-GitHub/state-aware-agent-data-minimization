# 四轮强基线对照与论文下一步

## 论文现在可以写什么

现有结果可以支撑一篇围绕**动态取数校验与任务恢复**的系统论文初稿。业务状态变化时，原来合理的读取可能失去依据。平台可在真正交付数据前重新校验，让 Agent 根据反馈继续处理剩余任务。

在 120 个冻结合成任务的自主模型实验中，相对 Agent 自行按需读取，后端校验把依据过期后仍交付的字段从 144 降到 0。两组业务完成均为 359/360。后端实际拦截 120 次，其中 119 条任务完成。后端组仍有一次在最终回答中复述合法已读字段，调用数差异的区间跨零。论文应把读入模型的数据、实际回答泄露和调用开销作为不同指标。[自主模型主报告](../necessity-three-arm-holdout/REPORT.md)

后续四轮问的是另一件事：允许一个做得好的字段表基线刷新状态和复用规则后，契约推导还有多少额外价值？这四轮没有调用模型，均使用脚本驱动模拟工具。它们约束了论文的配置优势主张，也为自主模型对照提供了可运行的基线。

业务层共同使用可信状态、用户授权、执行确认和恢复逻辑。身份核验、站点核验及签收核验的复用也属于共同能力。签收规则的配置数是在为两组分别编写迁移适配器后统计的。适配器开发工时、一般规则维护成本和真实服务延迟尚无实测。

实施入口依次为[读前刷新字段表与身份复用](../necessity_v2/route_baseline.py)、[字段表组合](../necessity_v2/composable_routes.py)、[签收规则迁移与核验复用](../necessity_v2/signature_rule.py)。

## 结论与写作顺序

1. 先写问题定义、方法和结果。主张聚焦给定结构化工具契约和可信状态下的动态取数约束、旧理由失效与授权内恢复。把自主模型对照与离线机制验证各自的比较对象写清楚。
2. 把与强基线相当的结果放进主文或结果表。后续三个物流研究说明，字段表获得组合和规则复用能力后，也能正确处理新组合和新增签收规则。目前证据尚未建立契约推导的配置优势，也未建立端到端泄露或调用效率优势。
3. 优先补下面的一轮自主模型对照。新任务应优先选能区分两种机制的情形，继续收集相同类型的脚本订单对论文主张帮助有限。

## 投稿前优先验证

**用同一个模型自主调用工具，比较可组合字段表与契约推导。** 目的是检验两组在脚本走查中观察到的一致性，在模型自行决定读什么、何时重试时能否保持。

- 共用工具 schema 与回包格式、授权、用户偏好、确认逻辑、恢复反馈、预算和模型。字段表按每次读前刷新的状态和规则放行。契约方案按步骤推导字段并重验取数理由。若凭据操作带来额外调用，事前明确内置检查和外部调用各如何记账。
- 先做开发走查，冻结两组实现后，再用小批新状态组合。覆盖原时段保留、额外核验、首选时段失效或恢复、授权不足、旧核验失效和已提交业务效果的续接。环境在相同业务边界触发事件，独立于模型是否发起某个读请求。
- 用独立业务账本核对业务完成、预期安全停止、误拒、过期或额外字段交付、重复执行和实际输出泄露。记录读取尝试、恢复、工具/模型调用及确认次数。逐组保留所有失败轨迹，按任务配对报告结果。
- 如果两组仍然相当，论文贡献可定位为动态取数机制及其适用边界，并把可组合字段表作为有效替代。如果出现差异，先核对回包结构、预算和事件触发，再定位差异来自哪项机制。

本页只整理已完成实验及后续设计。这轮自主模型对照尚未运行。

## 离线复跑

在仓库根目录执行：

```bash
python3 -B scripts/run_route_table_comparison.py --out route-table-comparison/trace.json
python3 -B scripts/run_logistics_composition.py compare
python3 -B scripts/run_logistics_dependency.py compare
python3 -B scripts/run_logistics_signature.py run
python3 -B -m unittest discover -s tests
```

这些命令使用仓库内的合成数据与本地脚本。运行器会重写各自的结果 JSON，建议在独立工作目录复跑以便核对结果字节。四轮材料直接放在对应目录。
